# Adhan config cleanup: drop audit history, pending offset, reason, and shift effectiveFrom to today

This change strips the Adhan config feature down to its core CRUD + preview flow. The history/audit trail (frontend `HistorySection`, backend `getHistory`/`revert` endpoints, `audit()` private method and all call sites, `AdhanConfigAudit` model and its type) is gone entirely. The "pending offset" concept is removed. `effectiveFrom` now defaults to today instead of tomorrow, so saves take effect immediately. The `isCustomized` badge on prayer cards now derives from the raw base version rather than the period-merged effective settings, so seasonal periods no longer falsely mark a prayer as customized. The `reason` field is gone from `ReviewDialog` and the save flow. Both repos typecheck clean and no test files reference the removed code.

**Watch for:** the `reason` machinery in `useAdhanDraft.ts` is now dead code left behind (interface field, `SET_REASON` action, `setReason` callback, `reason: ''` in `emptyDraft`) — nothing reads it anymore. The backend `CreatePeriodDto`/`UpdatePeriodDto` still declare an optional `reason?` that the service never persists (the `AdhanConfigPeriod` table has no reason column), and `CreateVersionDto.reason?` is still persisted to the `AdhanConfigVersion.reason` column but the UI never sends it, so that column is now always null. The `// ── Audit ──` section header in `adhan-config.service.ts` is orphaned directly above `// ── GET /adhan-config ──` with no method under it, and the file's top doc comment still advertises "audit logging". No Prisma migration drops the `AdhanConfigAudit` table, so the schema file change isn't propagated to any deployed DB.

**Verdict**: NEEDS_CHANGES

## High-level view

The design choices that matter: `isCustomized` on prayer cards now reads the raw base version rather than the period-merged effective settings, and `effectiveFrom` defaults to today so saves land immediately rather than tomorrow. The removed symbols (history endpoints, audit model, revert, pendingOffset, nextPendingSettings) have no remaining references in code or tests, and both repos compile.

The `reason` field lives on in three places that no longer connect to each other: the UI draft hook still carries it (but never sends it), the backend version DTO still accepts it and persists it to a column nothing reads, and the period DTOs accept it but the period table has no such column so it's silently dropped. None of this breaks a save, but it's cruft the stated cleanup goal implies should be finished.

The operational gap is the missing Prisma migration. Removing `AdhanConfigAudit` from `schema.prisma` drops it from the model, but without a `prisma migrate dev` there's no `DROP TABLE` applied to any existing database, so deployed environments keep a stale `AdhanConfigAudit` table. It's a one-command fix but needs to happen before this ships.

<summary>Details</summary>

### useAdhanDraft: immediate-save path works, but reason is dead code (confirmed)

`effectiveFrom` now seeds to today in `emptyDraft` and the `serverToday` effect dispatches `SET_EFFECTIVE_FROM` with the raw server date; the `tomorrowFrom` helper is gone. The backend's `createVersion` guard rejects `dto.effectiveFrom < today`, which still accepts `today` (strict less-than), so an immediate save does not trip the past-date guard.

The `reason` field is the loose thread. `AdhanDraft` still declares `reason: string`, the reducer still has `SET_REASON`, the hook still exports `setReason`, and `emptyDraft` still sets `reason: ''`. A repo-wide search for `setReason`, `SET_REASON`, and `.reason` returns nothing — the ReviewDialog reason input is gone and `applyBaseVersion` dropped its `reason` parameter — so this is pure dead code left over from the "remove reason" task.

### PrayerCard isCustomized: now keyed off the raw base version (confirmed)

`isCustomized` now reads `baseSettings?.prayers[prayer]` (the un-merged base version) instead of the period-merged `effective.perPrayer[prayer]`. This is the intended fix: previously a prayer whose offset came only from an active period would show "Customized" even though the base version had no permanent customization. Periods are still surfaced separately via the existing `hasPeriod` / `activePeriodLabels` path. The page derives `baseSettings` via `configToSettings`, which finds the base version by `effective.baseVersionId` and parses its raw `settings` — explicitly not the merged effective, per the comment at the top of the page.

### Backend service: audit fully removed, two cosmetic leftovers (confirmed)

All CRUD/preview paths are present and complete: `getConfig`, `getCatalog`, `preview`, `createVersion`, `createPeriod`, `updatePeriod`, `deletePeriod`. Each write still does optimistic locking, preview-token consumption, settings validation, and cache invalidation over the affected date range; removing the `audit()` calls did not affect any of this since audit was purely auxiliary logging.

The `audit()` private method is gone, and a repo-wide search confirms no `.audit(` or `adhanConfigAudit` references remain in the engine. Two cosmetic leftovers: the `// ── Audit ──` section header now sits directly above `// ── GET /adhan-config ──` with nothing between them, and the file's top doc comment still lists "audit logging" among the service's responsibilities.

### Backend reason field: inconsistent across the three write paths (confirmed)

The cleanup removed reason from the UI but left the backend half-removed in an inconsistent state. `createVersion` still does `reason: dto.reason ?? null` when persisting to `AdhanConfigVersion` (which has a `reason String?` column in both schema and migration), so a version row now always gets `reason = null`. `createPeriod` and `updatePeriod` never read `dto.reason` at all — the `AdhanConfigPeriod` table has no reason column — yet `CreatePeriodDto` and `UpdatePeriodDto` still declare `reason?: string`. So: the version DTO's reason is persisted-but-always-null, the period DTOs' reason is accepted-then-dropped. Since the UI no longer sends reason anywhere, all three `reason?` DTO fields are dead. Either remove them (and the `AdhanConfigVersion.reason` column + its migration) or leave a comment saying reason is retained for future manual/seed use.

### Prisma schema: AdhanConfigAudit model removed, but no drop migration (likely)

`schema.prisma` no longer declares `model AdhanConfigAudit`, and the `AdhanConfigAuditRecord` TS type was removed from `adhan-config.types.ts`. The existing migration `20261019052924_adhan_config` created the `AdhanConfigAudit` table, but there's no new migration to drop it. Without a `prisma migrate dev`, deployed databases keep the table (and any rows already in it), and the generated Prisma client still ships the `adhanConfigAudit` delegate until `prisma generate` runs. The code doesn't reference the delegate anymore, so this won't cause a runtime error, but the schema change is only half-applied. A single `prisma migrate dev --name drop_adhan_audit` would generate the `DROP TABLE` and regenerate the client.

### Test coverage

No spec or test file in either repo references the removed symbols (searched for `HistorySection`, `fetchAdhanHistory`, `revertHistory`, `AdhanConfigAudit`, `adhanConfigAudit`, `getHistory`, `revert`, `pendingOffset`, `nextPendingSettings`, `/history`). The engine's existing specs (`adhan-catalog.spec.ts`, `adhan-config.validator.spec.ts`, `adhan-config.resolver.spec.ts`) don't touch the audit/history surface, so they're unaffected.
